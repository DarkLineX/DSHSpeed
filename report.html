二 · 优化点，按性价比排序

01

消灭 Start-Sleep 轮询

−59.9 h · 10.7%
4,770 次 pwsh 里带 Start-Sleep，实测墙钟 59.9 小时。 这意味着 pwsh 跑的 162.7 小时里，有 37% 什么都没干，就在 sleep。

≥120 秒的 475 次独占 29.6 小时，这些几乎必然是超调——固定睡 600 秒，而活儿 90 秒就完了。 最长单次 3,388 秒（Start registration keepalive watchdog）。 叠加 job_output wait:true 的 952 次 / 31.3 小时，两者合计 91.2h = 总墙钟 16.4%。

改法：等外部进程结束一律用 job_output(wait:true, timeout_ms)； 真要定时采样，让后台作业自己在完成时写标记文件，主流程用一次阻塞等待取代 N 次 sleep。

04

上下文再压一档（TTFT 的直接杠杆）

−9.8 h · 1.8%
TTFT 只随"总上下文长度"增长，不随"缓存未命中的新增 token"增长。 opendesign 按 cache-miss 分桶 TTFT 是 3.2 / 3.5 / 3.4 / 2.7 / 4.1s——完全平； 按总上下文分桶是 2.2 / 3.1 / 4.0 / 4.1 / 3.4s。贵的不是新内容，是已缓存前缀的绝对长度。

现状：输入 p50 117,925 tok、p90 255,559、p99 689,716、max 919,932；cache 命中率 p50 99%。 最近 7 天 p50 已涨到 132,170、p90 367,355，14.4% 的步输入 >300k。

把所有 >120k 的步压到 <120k 水平，TTFT 省 9.77h（涉及 40,737 步）。

已做的：thresholdRatio 从 0.8 降到 0.45（opendesign 0.4）， 压缩触发点从 838,400 提前到 419,200，这一项已经吃掉 9.77h 里的大头。 若想再压，thresholdRatio 再降到 0.30（触发点 314,400）。
05

轮询链合并

−5.6 h · 1.0%
连续"唯一工具是 sleep / job-wait"的链：4,050 条、5,735 步、跨度 43.06h， 其中模型往返 18.97h。链长 p50=1、p90=2、max=14；≥5 次的 63 条。 每条链从 N 次压到 1 次 → 省模型往返 5.61h。

改法：一次 job_output(wait:true, timeout_ms:<预期完成时间>) 拿到结果， 不要连发三次探测。timeout 不要一律填 600000——现在 300000 用了 175 次、600000 用了 145 次， 而 p50 实际完成时间只有 54 秒。
06

修重试

−4.4 h · 0.8%
带重试的步 359 个（0.43%），TTFT p50 20.5s（干净步 4.8s），合计 LLM 8.21h， 其中超额 4.4h——一次重试的代价约等于一次完整往返。

已修：opendesign 的 streamIdleTimeoutMs 从 90,000 改回默认 300,000 （cordis.patch.yml:192）。原来 90 秒门槛砍掉了 66 条还在出字的流， 其中 42 条 30 秒内就恢复了——是误砍。

四 · 不要做的事（有数据排除）

  • 不要为了速度切 provider。这条已按你的要求整条撤掉——套餐余额决定路由，不参与优化。 报告旧版里那套 provider 排序全部作废。
  • 并发不是瓶颈。同一时刻 1 路并发 TTFT p50 为 3.3s，5–8 路并发反而降到 2.2s—— 多开几个会话不会互相拖慢（排队在 provider 侧，不在本地）。
  • "每步并发多工具省 127.6h"是错的，已撤回。实测：单工具·只读 17.6%、 单工具·写操作 72.3%（有依赖不可合并）、多工具已并行 7.0%。 连续只读步段 2,695 段覆盖 9.8% 的步，2 合 1 只省 9.0h = 3.4%。 而且 pwsh 单工具步 43,807 中 96.7% 本来就是「一条命令多条语句」。 工具执行器本身是真并发（5,648 个多工具步串行度均值 1.17，4 个 read 起始散布 1–2ms）—— 基础设施没问题，问题是合并空间本就极小。
  • catalog 瘦身只省账单，不省时间。62 个死工具加权 6,601 chars ≈ 2,063 tok/请求， 是 catalog 的 15.3%，但只占中位 prompt 的 1.8%。 由于 TTFT 不随新增 token 变化，删掉它们对速度几乎无影响。 （workflow 4,430 chars 出现在 99% 的请求里、调用 0 次；subagent_fork 1,504/99%/0 次。）
  • compaction 不是瓶颈。11,717 次仅耗 1.98h（失败 11,710 次，浪费 1.95h = 0.35%）。 但它是「输出 token 上限截断」的根因，见下节。

五 · 顺带查出来的三个问题

5.1 输出 token 上限截断 = compaction 失败，不是"输出太多"

全库 81,662 条 assistant 消息里 stopReason=length 只有 9 条， 其中 7 条根本不是输出太多——maxTokens=null 或 128,000，输出只有 366/625/966/1,387/2,041/16/16 token， 内容块只有 reasoning。

因果链：compaction 摘要被上游判 length → dsh-compaction-basic 的 finishError() 抛 MAX_TOKENS → 压缩失败 → 上下文不降 → 下一步又撞 → dsh-agent-loop:966 if (finish.kind === "max-tokens") return { kind: "max-tokens" } → turn 结束弹横幅。

dsh-agent-loop:770 还有个粘滞逻辑：if (turnEnds === null || turnEnds.kind !== "max-tokens") turnEnds = stepEnd; ——一旦 turn 内出现过 max-tokens，后续 step 覆盖不掉。

为什么以前看不到：compaction/end 全库 11,717 次，成功 7 次。 billion-context 用 dsh_compaction_refused 拦掉了 11,674 次（99.7%）。 关掉它，原生压缩路径才第一次真正跑起来。

已修：整份覆盖 preset-standard 把 compaction 配置写进去—— thresholdRatio 0.45（opendesign 0.4）、maxTokens 32768、 retainRatio 0.12、compactionRetries 2。 两条路都堵住：装了 billion-context → 走快照；卸了 → 我的配置生效。

原生路径已能跑通的证据：2026-11-11 12:15:27 whatsapp-android 会话， compaction/end dur=27.44s error=null，摘要是真正的 LLM 总结（不是 <bili-snapshot>）。 上一次原生 LLM 摘要成功是 2026-09-24——中间 48 天一次都没成功过。 全库 11,717 次 compaction 里，成功的只有 7 次（4 次快照 + 3 次原生）。

5.2 昨晚卡十几小时 = Windows 空闲睡眠

Power-Troubleshooter 日志铁证：2026-11-10 19:44:26 → 2026-11-11 09:55:20 睡了 14h10m54s （唤醒源 Intel USB 3.20 控制器）。另有一次 16:38:44 → 16:49:45（11m01s）。 全库 40 条睡眠记录合计 645.5 小时。

原因：powercfg /q 显示 AC 下 STANDBYIDLE = 0x00000708 = 1800 秒（30 分钟空闲即睡）。 DSH 自身完全没有保活机制——resources 全量扫（含 213MB 的 app.asar 备份） powerSaveBlocker / SetThreadExecutionState / ES_SYSTEM_REQUIRED / prevent-app-suspension 全部 0 命中；powerMonitor 只在 resume 时查更新。

冻住的现场：Pixel4Root turn9 卡 14h13m、SrcAntiDex turn2 卡 14h10m、 whatsapp-android turn11 卡 14h56m——都是醒来后靠 RETRY 才恢复。 11-10 16:00 → 11-11 10:10 窗口内 16 个 ≥20m 的 turn，clockspan 52.83h 里 42.55h 是睡着的（80.5%）。

已修：powercfg /change standby-timeout-ac 0，复核 AC 下 STANDBYIDLE = 0x00000000 （永不睡眠）、HIBERNATEIDLE = 0x00000000。关屏仍是 600 秒，不影响执行。不需要重启。

5.3 装插件会杀掉正在跑的 turn

全库 aborted/disposed 11 次、5 波，其中 2026-11-10 18:10:18 一波 4 个会话同时被杀， 合计 2h56m 在飞工作被丢、输出 87 万 token 作废。

四波全部对得上 plugin_manager 触发的 pnpm 操作 mtime： 10-15 13:44:39 ← operation-nKUOfW 13:45:05； 11-05 18:53:58 ← operation-rVXQQj 18:51:57； 11-10 18:10:18 ← operation-7TqLuF 18:09:15（58 秒前）； 11-10 18:59:00 ← operation-92EjWR 18:58:52（8 秒前）。

源码路径：dsh-agent-loop:1496 machine.cancel({ kind: "disposed" }, ...) ——agent scope 拆除时取消所有在飞 turn。 dsh-goal-round-driver:279 更狠：if (event.data.reason.reason.kind === "disposed") { disarm(state); return; } ——goal 自动续跑直接解除武装，不会自己恢复。

改法：装/卸插件挑没有长任务在跑的时候。目前无法热装。

八 · 口径与可复现

口径
  • 时间来自会话日志的完整回放，不采样；区间按并集去重后再相加，避免工具窗口与 LLM 窗口重复计。

  • reasoning token 是字符数 ÷ 4 估算；上报 outputTokens 与估算的比值是 1.28，说明 reasoning 被折进 output。

复现脚本（C:\Users\admin\Desktop\DSHSpeed\.probe\，用 bundled node 跑）：
  • opt16.mjs — 557h 五分区（最权威）
  • opt18.mjs — Start-Sleep 解剖 + 加权死 catalog
  • opt21.mjs — TTFT vs 缓存未命中 / vs 总上下文 / effort 匹配对比
  • opt19.mjs — 并发对 TTFT 的影响（证明无关）
  • opt9.mjs / opt12.mjs — 重复 read / 轮询链
  • compact.mjs — compaction 全量成败
  • hang5.mjs / gapclass.mjs — 睡眠窗口与 gap 分类
  • kill.mjs — disposed 杀 turn 与 pnpm 操作关联

解析坑（每一个都踩过）：
  • 日志是多帧 zstd 拼接，按 magic 28 B5 2F FD 切帧逐帧解，单次调用只解第一帧。
  • usage 在 data.usage，不是 data.message.usage。
  • 块时长只能 sum(c.dt)；time0 是请求起始时间的拷贝，不能当耗时。
  • 块类型看 c.chunk.blockType（只在 block-start 里），读 c.type 会全部错配。
  • time 是 epoch ms UTC，+8h 才是本地时间。
  • tool/result 的 isError 不可信（85 万级样本只有 1.4% 标 true，连 fatal: not a git repository 都标 false）；判失败要看 callId 是否出现在任何 tool/result 里。
